Motivation & Problem Statement
Why IRCTC breaks — and what ScaleRail does differently

IRCTC is one of the most traffic-stressed web applications in the world. On Tatkal booking days, millions of users simultaneously hammer a single endpoint at 10:00 AM sharp, creating a thundering-herd spike unlike almost any other consumer application.

The Real-World ProblemIRCTC regularly crashes under Tatkal load, shows "seat available" only to reject the booking seconds later, issues duplicate PNRs in rare cases, and fails to refund on time after cancellations. These are not just UX problems — they are distributed systems engineering failures.

What ScaleRail was built to study

🪑
Double Booking
Two users buy the same seat at the same millisecond. ScaleRail uses Redis distributed Lua locks + PostgreSQL FOR UPDATE NOWAIT + CAS versioning — three independent layers to prevent this.
Race condition
💥
Partial Failures
Payment succeeds but booking doesn't confirm. ScaleRail implements the Saga Orchestration pattern with compensating transactions and a persistent SagaLog for auditability and crash recovery.
Distributed saga
🔁
Duplicate Requests
Network retries can cause double-charges. ScaleRail uses client-provided idempotency keys on every mutation — any retry returns the cached response instantly, guaranteed.
Idempotency
🔍
Unusable Search
IRCTC requires exact station name spelling. ScaleRail uses Elasticsearch multi_match + fuzziness:AUTO, supporting typos and station codes across 500+ stations at sub-100ms latency.
Full-text search
🗺️
No Segment Booking
ScaleRail supports partial-route booking: a seat from Delhi→Mumbai can be sold to one passenger for Delhi→Agra and another for Mathura→Mumbai — maximizing capacity utilization.
Segment logic
📧
Synchronous Notifications
ScaleRail decouples notifications entirely via Kafka — the booking API returns before the email is sent. A notification failure cannot roll back a confirmed booking.
Async messaging

Requirements
Functional and non-functional constraints that shaped every decision

Functional Requirements

  • User registration — OTP email verification before account creation
  • Login — Password + Google OAuth, device-aware sessions
  • Train search — Fuzzy by station name/code, date-filtered, seat count summary
  • Seat selection — Per-class view, segment-aware availability
  • Booking + payment — Seat lock → Razorpay order → pay → confirm
  • Cancellation & refund — Cancel pre-departure; auto-refund if payment captured
  • Booking history — Paginated; filterable by status
  • Admin CRUD — Stations, trains, routes, schedules
  • Email notifications — OTP, welcome, booking confirmed, cancelled
  • Segment booking — Sell non-overlapping segments on same seat independently

Non-Functional Requirements

  • No double-booking — Three independent concurrency guards
  • Idempotency — All mutations safe to retry
  • CP over AP for seats — A booking rejection is better than a double-booking
  • Fault isolation — Notification failure must not roll back confirmed bookings
  • Async by default — Email, search index updates are async via Kafka
  • Observability — Structured JSON logs; Kafka UI; Redis Insight; Kibana; pgAdmin
  • Graceful shutdown — SIGTERM handled; in-flight requests complete before exit
  • Horizontal scalability — All services stateless; shared state in Redis/Postgres/Kafka
  • Resilience — Dead-letter queues; saga compensation on any step failure
Core Design Philosophy"Async where possible, synchronous only where consistency demands it." Seat locking and payment creation are synchronous. Email, search index updates, and analytics are asynchronous.

Major Components — and Why They Were Chosen
The reasoning behind every technology in the stack

PostgreSQL — The Source of Truth

Why Postgres over MongoDB/DynamoDB? Seat inventory is inherently relational. More critically, Postgres provides SELECT ... FOR UPDATE NOWAIT — a row-level pessimistic lock that's the backstop against double-booking if Redis temporarily fails. Transactions and ACID guarantees are non-negotiable for money and seat inventory.

Key Postgres feature: FOR UPDATE NOWAITMeans "lock these rows exclusively right now, or fail immediately." This prevents Postgres from waiting in a queue — it throws a conflict error instantly, converted to a 409 CONFLICT for the user. No deadlock risk, no ghost bookings.

Redis Stack — Cache, Locks, and Sessions

Distributed Seat Locks
Lua scripts for atomic multi-seat lock acquisition. Pattern: booking:lock:seat:{scheduleId}:{seatId}:{fromSeq}:{toSeq}. TTL-based auto-expiry prevents orphaned locks even if the service crashes.
Session & OTP Storage
OTPs stored as otp:session:{id} with 10-min TTL. Refresh token JTIs stored as refresh:{userId}:{deviceId} for per-device rotation. User profile cached for read acceleration.
Leader Election
Booking expiry job uses SET NX EX to elect one instance as leader per cycle, preventing all replicas from redundantly scanning the DB for expired bookings simultaneously.
Why Redis for locks instead of Postgres advisory locks?Redis SETEX is sub-millisecond. Postgres advisory locks are connection-scoped — if the connection drops, the lock may not release cleanly. Redis TTL provides automatic orphan cleanup regardless of how the process exits.

Apache Kafka — Event Bus for Async Workflows

Why Kafka over RabbitMQ or direct HTTP calls?

  • Durability — Messages persist to disk. If notification-service is down, it processes the email when it recovers. RabbitMQ loses unacknowledged in-memory messages.
  • Replayability — Elasticsearch down? Kafka replays all events from last committed offset when it recovers.
  • Fan-out — One booking.confirmed event is consumed by notification-service AND can later be consumed by analytics, loyalty — zero coupling changes needed.
  • Dead Letter Queues — After 3 retries, poison messages route to dlq.{service} topics, visible in Kafka UI for manual replay.

Elasticsearch — Fuzzy Station Search

Why not Postgres ILIKE? ILIKE '%Mumbai%' requires a full table scan (no index on substrings) and can't handle "Mumbay" (typo). Elasticsearch multi_match with fuzziness: AUTO handles typos via edit distance, partial matches, and relevance scoring — all at sub-100ms latency.

// The search query strategy in search-service
{
  "bool": {
    "must": [
      { "multi_match": { "query": "DEL", "fields": ["fromStation.name","fromStation.code"], "fuzziness": "AUTO" }},
      { "multi_match": { "query": "MUM", "fields": ["toStation.name","toStation.code"],   "fuzziness": "AUTO" }}
    ],
    "filter": [
      { "term":  { "departureDate": "2025-01-15" }},
      { "range": { "seatSummary.total": { "gt": 0 }}}  // Only trains with seats
    ]
  }
}

The Elasticsearch index is denormalized — includes seat summary counts. Updated asynchronously via Kafka inventory.seat-availability-updated events. Search results may be seconds stale (acceptable) — the real-time check happens when the user clicks "Book."

Razorpay — Payment Gateway

  • Dual verification path: Webhook from Razorpay + client-side verify call. Whichever arrives first confirms the booking; the second is idempotent.
  • HMAC on raw bytes: Raw request buffer (not parsed JSON) is HMAC-SHA256'd. JSON parsing would change bytes and break the signature — a real gotcha.
  • Refund idempotency: Every refund uses {bookingId}-cancel-refund as key to prevent double-refunds on retry.

Database & Schema Design
Per-service database isolation — no cross-service joins, ever
Core Principle: No Shared DatabasesEach service owns its schema. Cross-service data access happens only via synchronous REST calls or async Kafka events. This enables independent deployment, schema evolution, and prevents the "distributed monolith" anti-pattern.
-- booking-service/prisma/schema.prisma

enum BookingStatus {
  PENDING, SEATS_HELD, PAYMENT_PENDING, CONFIRMING,
  CONFIRMED, CANCELLING, FAILED, CANCELLED, EXPIRED
}

model Booking {
  id             UUID          @id @default(uuid())
  userId         UUID          -- NOT a FK; cross-service boundary
  scheduleId     UUID
  trainId, trainNumber, trainName  -- DENORMALIZED: works even if train deleted
  departureDate  DATE
  status         BookingStatus @default(PENDING)
  totalAmount    FLOAT         -- in paise (rupees × 100)
  fromStationId  UUID?         -- SEGMENT BOOKING: boarding station
  toStationId    UUID?         -- SEGMENT BOOKING: alighting station
  fromSeq        INT?          -- SEGMENT BOOKING: sequence number
  toSeq          INT?          -- SEGMENT BOOKING: sequence number
  idempotencyKey VARCHAR       @unique
  paymentOrderId VARCHAR?      @unique

  version        INT           @default(0)  -- CAS optimistic lock counter

  @@index([lockExpiresAt, status])  -- expiry job scans this
  @@index([userId])
  @@index([scheduleId])

Authentication & Security
Three-layer auth: JWT, internal service auth, and webhook HMAC verification

JWT + Refresh Token Architecture (RTR Model)

LOGIN POST /api/users/auth/login → { accessToken (15 min) } + Set-Cookie: refreshToken (7d, HttpOnly, SameSite=Strict) accessToken: stored in memory (Zustand) — NEVER localStorage refreshToken: HTTP-only cookie — JavaScript cannot read it EVERY REQUEST Authorization: Bearer {accessToken} API Gateway: verifies JWT signature → injects X-User-Id + X-Internal-Secret TOKEN EXPIRY (401 received) Axios interceptor → POST /auth/refresh (cookie sent automatically by browser) User Service: 1. Verify refresh token JWT signature 2. Extract jti (JWT unique ID) 3. Look up Redis: refresh:{userId}:{deviceId} — must match stored jti 4. If MISMATCH: DELETE Redis key (stolen token!) → both parties forced to re-login 5. If match: new accessToken + new refreshToken (rotated) + update Redis Axios: retries original request with new token THEFT DETECTION Attacker uses old refreshToken after rotation: Redis has new jti → mismatch detected → DELETE key → both forced to re-login This is the Refresh Token Rotation (RTR) security model

Internal Service Authentication

All service-to-service calls carry X-Internal-Secret header injected by the API Gateway. Each downstream service validates it on /internal/* routes, preventing anyone who discovers an internal port from calling those endpoints directly.

Razorpay Webhook Verification

// Payment Service — webhook handler (raw body is CRITICAL)
const body      = req.rawBody;  // raw Buffer, NOT parsed JSON — see API Gateway special case
const signature = req.headers['x-razorpay-signature'];
const digest = crypto
  .createHmac('sha256', RAZORPAY_WEBHOOK_SECRET)
  .update(body)
  .digest('hex');
if (digest !== signature) throw new UnauthorizedError('Invalid webhook signature');
Why raw body mattersThe API Gateway applies express.raw() (not express.json()) for the webhook path. JSON parsing changes whitespace, numeric precision, and key ordering — any change breaks the HMAC. This is the #1 reason payment webhooks silently fail.

Other Security Controls

  • Helmet.js — CSP, X-Frame-Options, X-XSS-Protection
  • CORS — Explicit origin allowlist; credentials: true for cookie auth
  • Rate limiting — At API Gateway; prevents brute-force and scraping
  • bcrypt — Password hashing with cost factor 12 (deliberately slow)
  • Google OAuth — ID token verified server-side via google-auth-library; no client-side trust

Concurrency & Consistency
The three-layer defense against double-booking
The Core ProblemTwo users hit "Book" at the same millisecond for the same seat. Both see AVAILABLE. Both call /api/bookings. Without proper locking, both succeed — a double-booking. This is exactly what happens on IRCTC during Tatkal.

Layer 1 — Redis Distributed Lock (First Line of Defense)

-- Lua script: acquire ALL locks atomically, or acquire NONE (runs on Redis server)
local lockValue = ARGV[1]  -- bookingId:timestamp (unique owner identity)
local ttl = tonumber(ARGV[2])
local acquired = {}

for i, key in ipairs(KEYS) do
  local result = redis.call('SET', key, lockValue, 'NX', 'EX', ttl)  -- SET if Not eXists
  if not result then
    for j = 1, #acquired do redis.call('DEL', acquired[j]) end  -- rollback
    return 0  -- fail: another user has this seat
  end
  table.insert(acquired, key)
end
return 1  -- success: all seats locked for this user

Why Lua? Lua scripts run atomically on the Redis server — no other commands can interleave. Without Lua, there's a TOCTOU race between checking key existence and setting it.

Deadlock prevention: seatIds are sorted alphabetically before building lock keys. Concurrent requests for the same seats always acquire locks in the same order, preventing circular wait.

Layer 2 — PostgreSQL Row-Level Lock (Backstop)

-- Inside inventory-service lockSeats(), in a Postgres transaction:
SELECT id, "seatId", status
FROM seat_inventories
WHERE "scheduleId" = ${scheduleId}
  AND "seatId" = ANY(${seatIds}::text[])
FOR UPDATE NOWAIT;
-- NOWAIT: if another transaction holds these row locks,
-- immediately throw — NOT wait in queue.
-- This is the safety net if Redis is temporarily unavailable.

Layer 3 — Optimistic Locking / CAS (State Machine Guard)

// casUpdateBooking — Compare-And-Swap on booking status
const result = await prisma.booking.updateMany({
  where: { id: bookingId, version: expectedVersion },  // must match what we read
  data:  { status: newStatus, version: { increment: 1 } },  // atomic increment
});
if (result.count === 0) throw new StaleStateError(...);

CAS prevents three-way races: payment webhook + user cancel + expiry job all hitting the same booking simultaneously. Only one claims it (increments version); others get StaleStateError and skip gracefully.

Segment Booking Concurrency

-- Postgres: check for overlapping segment locks (the interval overlap algorithm)
SELECT "seatId" FROM seat_segment_locks
WHERE "scheduleId" = ${scheduleId}
  AND "seatId" = ANY(${seatIds}::text[])
  AND status IN ('LOCKED', 'BOOKED')
  AND "fromSeq" < ${toSeq}   -- a.from < b.to  (overlap condition)
  AND "toSeq" > ${fromSeq}   -- b.from < a.to  (overlap condition)
FOR UPDATE NOWAIT;

Two users booking non-overlapping segments (A→B and C→D) on the same seat get different Redis lock keys and can proceed concurrently. Overlapping segments are caught by the SQL above.

Expiry Job Leader Election

// Redis SET NX EX: "set if not exists, expire in 25s"
const result = await redis.set(
  'booking:expiry-job:leader', process.pid.toString(), 'NX', 'EX', 25
);
// Only the winning instance runs cleanExpiredBookings() this cycle.
// TTL (25s) < interval (30s) so the leader re-races each cycle.
// If leader crashes, lock expires and another instance takes over.

Scalability & Performance
How the system handles 10× and 100× load increases

What Makes Each Layer Scalable

Services (stateless)
No in-process state. All mutable state lives in Postgres/Redis/Kafka. Add more pods, get proportionally more capacity. Kubernetes HPA can auto-scale based on CPU or custom metrics.

Key-based sharding. Lock keys are namespaced by scheduleId, so seats on different trains shard to different Redis nodes — near-perfect horizontal distribution.
Kafka (partitions)
Add partitions to scale consumer parallelism. Each notification service replica is a consumer group member — partitions distribute load automatically.

The Toughest Engineering Problems Solved
The problems that took the longest to get right

Problem 1: Segment Booking + Concurrency

The hardest problem in the system. A seat should be sellable to Delhi→Agra AND Mathura→Mumbai simultaneously. But two users booking Delhi→Agra for the same seat must be caught.

Solution: Redis lock key includes segment (:fromSeq:toSeq) → same-segment conflicts caught by Lua NX. Postgres SeatSegmentLock table with interval overlap SQL catches overlapping-but-not-identical segments. The aggregate SeatInventory.status is recomputed by counting actual segment lock rows — never by arithmetic — to prevent counter drift.

Problem 2: Three-Way Race Condition on Booking Status

PAYMENT_PENDING booking simultaneously touched by: (1) payment webhook, (2) user cancellation, (3) expiry job — in three separate processes.

Solution: Compare-And-Swap using updateMany({ where: { id, version: N }, data: { ..., version: N+1 } }). Returns count: 0 if version already changed. The loser skips silently — no double-processing, no double-refund, no ghost booking. This is the Postgres equivalent of CAS without the complexity of transactions.

Problem 3: Razorpay Webhook Signature Breaking

Payment webhooks were failing signature verification silently. Payments went through on Razorpay's side but bookings never confirmed.

Root cause: API Gateway applied express.json() to ALL routes including the webhook. JSON parsing altered the bytes. HMAC computed on parsed body didn't match Razorpay's HMAC on raw bytes.

Solution: Special case in gateway middleware: if req.path === '/api/payments/webhooks/razorpay', apply express.raw({ type: 'application/json' }) instead. The raw Buffer is passed through — exact bytes Razorpay signed.

Problem 4: Seat Aggregate Counter Drift

The schedule_inventories.available counter was updated arithmetically: available = available - N. Under concurrent load, two transactions reading the same value and both subtracting led to the counter going negative or incorrect.

Solution: Replaced arithmetic updates with a full recount: COUNT(*) FILTER (WHERE status = 'AVAILABLE') from actual seat rows. Called recountScheduleAggregates() inside every transaction that changes seat status. Ground truth wins. Slower but absolutely correct.

Problem 5: Expiry Job Running on All Replicas Simultaneously

3 replicas of booking-service all ran the expiry job simultaneously → same expired booking processed 3 times → 3 emails sent, 3 seat releases, potential triple compensation.

Solution: Redis leader election via SET NX EX. Only the instance that wins the SET runs the cleanup. TTL (25s) is shorter than the interval (30s) so the leader re-races each cycle. If the leader crashes, the lock expires and another instance takes over automatically.

"What If" Interview Questions
Prepared answers for every interviewer follow-up

What if traffic is 10×?

Search: Scale Elasticsearch nodes + replicas + add gateway-level cache for popular routes (Redis, 30s TTL). Booking: Scale booking-service pods horizontally + add PgBouncer for connection pooling. Locks: Redis handles millions of ops/s — no concern. Notifications: Add more Kafka consumer group members — partitions scale linearly.

What if Postgres fails?

Production uses RDS Multi-AZ. Postgres promotes the standby in ~60 seconds automatically. Booking requests fail with 503 during failover. Kubernetes liveness probes restart pods after failover. No data loss (synchronous replication to standby). Read replicas: if one fails, Prisma connection string falls back to primary.

What if Redis fails?

  • Seat locks: acquireSeatLocks returns {acquired: false} (fail closed). Bookings rejected. Postgres FOR UPDATE NOWAIT still prevents double-booking but we can't track lock ownership without Redis. This is the correct conservative failure mode — reject rather than risk duplicates.
  • OTPs: Registration blocked. Login with existing password still works (DB-backed).
  • Sessions: Token refresh fails — users with expired access tokens get logged out.

What if Kafka fails?

Synchronous saga (lock → create payment order) does NOT use Kafka. Bookings and payments continue normally. Notifications won't send until Kafka recovers. When it does, the consumer reads from its last committed offset — no messages lost (persisted to disk). This is Kafka's key advantage over in-memory queues.

What if a booking is created but the service crashes before saving the idempotency record?

Client retries with same key. Booking record already exists. Idempotency check passes (record not saved). Saga re-runs: HOLD_SEATS re-executes. Inventory will check for existing segment locks — may succeed or fail depending on state. The correct fix is for saga steps to check SagaLog for already-completed steps before re-executing. This is a known limitation (see Section 17).

What if the same payment.success Kafka message is delivered twice?

handlePaymentSuccess has two guards: (1) checks booking.status === 'CONFIRMED' → returns early; (2) CAS update with version → second execution gets count: 0 → skips. These together give exactly-once semantics despite at-least-once delivery.

What if Razorpay is down?

CREATE_PAYMENT saga step fails. compensateHoldSeats runs → seats released. Booking → FAILED. User gets error suggesting retry. No partial state left — clean failure.

What if there's a network partition between booking-service and inventory-service?

HOLD_SEATS saga step times out and throws. Compensation runs (nothing to undo at this point). Booking → FAILED. Redis locks released. Inventory never knew about the booking — no orphaned lock anywhere. Clean failure with no data inconsistency.

What if a user double-clicks "Pay" and sends two booking requests?

Both requests carry the same client-generated idempotencyKey. The first request creates the booking and stores the response. The second request hits the idempotency check → finds the existing record → returns the same cached response immediately without executing any saga steps. This is by design.

Limitations & Future Improvements
Honest reflection + a roadmap of engineering problems left to solve

Known Limitations

⚠ Single-Broker Kafka (Dev)
Replication factor 1. If broker crashes, all events are lost. Production requires 3+ brokers with RF=3 and min ISR=2.
⚠ No Distributed Tracing
No trace ID propagated across service boundaries. Correlating a booking failure requires manual log grepping across 4 services.
⚠ Saga Crash Recovery Gap
If booking-service crashes mid-saga after HOLD_SEATS but before saving the idempotency record, a retry may re-execute HOLD_SEATS. SagaLog exists but saga steps don't check it before re-executing.
⚠ No Admin RBAC
Admin endpoints protected by internal secret but not by user role. Any authenticated user who discovers the admin API path can create schedules.
⚠ Idempotency Table Unbounded
No TTL or cleanup job. Will accumulate millions of rows over months. Needs a background pruning job.
⚠ No Virtual Waiting Room
Under Tatkal load, seats are first-come-first-served at API level. Users with better network connections win — not fair queuing.

Future Engineering Problems to Solve

⚡
gRPC & Protobuf Inter-Service Communication
Replace internal REST HTTP/1.1 calls (e.g. Booking → Inventory lock-seats) with gRPC over HTTP/2 using binary Protocol Buffers. Reduces serialization overhead by 5x-10x, eliminates text parsing costs, and enforces strongly-typed cross-service contracts.
High Performance RPC
📦
Transactional Outbox Pattern (Debezium CDC)
Solve the "Dual-Write Problem" (DB commit succeeds but Kafka publish fails). Write events to an outbox table in the SAME Postgres ACID transaction. Debezium Change Data Capture reads the Postgres WAL log and streams events to Kafka with 100% reliability.
Event Reliability
🛡️
Circuit Breakers & Bulkhead Isolation
Wrap internal microservice calls in Circuit Breakers (Opossum/Resilience) and Bulkhead thread pools. If inventory-service slows down, requests fail fast with fallback responses instead of stacking up and exhausting API Gateway connections.
Fault Tolerance
🎭

Serialize seat mutation requests using a single-threaded Actor pattern per train schedule backed by Redis Streams / BullMQ. Processes seat state updates sequentially in-memory, eliminating Postgres transaction lock contention entirely.

Architecture
The Deepest Unsolved Problem The segment booking + concurrent concurrency race is solved for the happy path. But under very high concurrency, when many concurrent transactions run recomputeSegmentSeatStatuses() simultaneously for overlapping seat sets, the FOR UPDATE NOWAIT approach makes one fail immediately — triggering the retryTransaction() loop. Under extreme load, this retry storm could itself become a bottleneck. The correct production solution: a dedicated single-threaded actor (Redis Streams consumer per seat) that serializes all mutations for a given seat, eliminating contention at the source.
