1. EXECUTIVE SUMMARY & SYSTEM OVERVIEW
================================================================================
ScaleRail is a production-grade, distributed microservices platform designed to 
re-engineer and solve the high-concurrency, consistency, and reliability failures 
encountered in real-world railway reservation systems such as IRCTC (Indian Railway 
Catering and Tourism Corporation).

System Snapshot:
- Architecture: Event-Driven Microservices (7 standalone domain services)
- Gateway: API Gateway with JWT validation, rate-limiting, proxy routing & raw-body routing
- Core Tech Stack: Node.js (v18), Express, Prisma ORM, React 18 + Vite, Zustand
- Datastores & Infra: PostgreSQL 15 (4 isolated DBs), Redis Stack 6.2, Apache Kafka (Confluent), Elasticsearch 8.12
- Payment Integration: Razorpay Gateway (Orders, Webhooks, Signature Verification, Refunds)

Key Highlights:
- 3-Layer Defense against Double-Booking (Redis Lua -> Postgres FOR UPDATE NOWAIT -> CAS Versioning)
- Segment-Aware Booking Algorithm (partial route seat optimization: A->B and C->D on same seat)
- Distributed Saga Orchestration for multi-service transactions with automatic compensation
- Event-driven async processing via Kafka for non-blocking notifications & Elasticsearch indexing

2. REAL-WORLD IRCTC PROBLEMS & MOTIVATION
================================================================================
IRCTC processes millions of concurrent requests during peak "Tatkal" (same-day premium) 
booking windows (e.g., 10:00 AM sharp). Under extreme thundering herd spikes, traditional 
monolithic or poorly partitioned architectures break down in distinct ways:

Problem 1: Double-Booking & Phantom Availability
  - IRCTC UX often shows "Seats Available", but upon payment completion, the seat is already 
    assigned to another user.
  - Root Cause: Lack of atomic multi-resource distributed locking, TOCTOU (Time-of-Check to 
    Time-of-Use) race conditions, and improper transaction isolation.

Problem 2: Payment Succeeded but Ticket Failed (Money Trapped)
  - Users get charged on payment gateways, but the booking status fails to update to CONFIRMED.
  - Root Cause: Distributed systems lack atomic transactions across service boundaries. Direct 
    synchronous HTTP calls fail mid-flight, leaving system state inconsistent without saga compensation.

Problem 3: Inefficient Seat Utilization (No Segment Booking)
  - A seat booked from Station A to B on a train running A -> B -> C -> D remains blocked for 
    the entire train journey even if vacant between B -> D.
  - Root Cause: Simplified global seat booking flags instead of fine-grained interval/segment locks.

Problem 4: Thundering Herd Search Crashes & Poor Search UX
  - Searching for trains with minor typos or station code mismatches fails completely or hammers 
    relational database tables with wildcard `LIKE` queries.
  - Root Cause: Relational DB used for full-text search instead of a dedicated search engine.

ScaleRail was engineered specifically to solve every single one of these problems.

NON-FUNCTIONAL REQUIREMENTS:
1. Consistency over Availability (CP System for Inventory): A seat booking request MUST fail fast (409 Conflict) rather than allow double-booking.
2. Strict Idempotency: Duplicate API calls or Kafka events must return identical responses without side-effects.
3. Sub-Second Seat Locking: Redis Lua lock execution < 10ms; total saga checkout initialization < 1.5s.
4. Async Decoupling: Non-critical operations (email, search indexing, analytics) executed asynchronously via Kafka.
5. Observability & Auditability: End-to-end JSON logging (Winston), Kafka UI, Redis Insight, Kibana log aggregation, Saga audit logs.

6. HARD PROBLEMS #1: CONCURRENCY, LOCKING & SEGMENT-AWARE BOOKING
================================================================================
Problem Statement:
Prevent two concurrent users from booking the same physical seat for overlapping journey segments, even if requests hit different gateway instances at the exact same millisecond.

SOLUTION: THE THREE-LAYER DEFENSE ARCHITECTURE

LAYER 1: Redis Distributed Lock with Atomic Lua Script (Fast Fail-Closed Layer)
- Key Pattern: `booking:lock:seat:{scheduleId}:{seatId}:{fromSeq}:{toSeq}`
- Deadlock Prevention: Seat IDs are sorted lexicographically before lock evaluation.
- Lua Script Logic:
  ```lua
  local lockValue = ARGV[1] -- bookingId:timestamp
  local ttl = tonumber(ARGV[2])
  local acquired = {}

  for i, key in ipairs(KEYS) do
    local result = redis.call('SET', key, lockValue, 'NX', 'EX', ttl)
    if not result then
      -- Rollback previously acquired keys in this batch
      for j = 1, #acquired do redis.call('DEL', acquired[j]) end
      return 0 -- Failed to acquire all locks
    end
    table.insert(acquired, key)
  end
  return 1 -- Success
  ```
- If any seat key exists, Lua immediately deletes all locks acquired in that batch and returns 0.

LAYER 2: PostgreSQL Row-Level Lock with FOR UPDATE NOWAIT (Database Backstop)
- When `inventory-service` executes `lockSeats()`, it executes inside a SQL transaction:
  ```sql
  SELECT "seatId", status 
  FROM seat_inventories 
  WHERE "scheduleId" = $1 AND "seatId" = ANY($2::text[]) 
  FOR UPDATE NOWAIT;
  ```
- `NOWAIT` behavior: If another transaction holds a row lock, Postgres throws error `55P03 (lock_not_available)` instantly. This prevents connection queue blocking and eliminates DB deadlock possibilities.
- Segment Overlap Query:
  ```sql
  SELECT "seatId" FROM seat_segment_locks
  WHERE "scheduleId" = $1 AND "seatId" = ANY($2::text[])
    AND status IN ('LOCKED', 'BOOKED')
    AND "fromSeq" < $4  -- Requested toSeq
    AND "toSeq" > $3    -- Requested fromSeq
  FOR UPDATE NOWAIT;
  ```
- Mathematical overlap condition: `Interval A overlaps Interval B iff (A.start < B.end AND A.end > B.start)`. If this query returns rows, the requested segment collides with an existing booking.

LAYER 3: Compare-And-Swap (CAS) Optimistic Concurrency Control (State Transition Guard)
- Every update to `Booking` or `SeatInventory` increments a `version` column.
- Atomic state update query pattern:
  ```javascript
  const result = await prisma.booking.updateMany({
    where: { id: bookingId, version: currentVersion },
    data: { status: newStatus, version: { increment: 1 } }
  });
  if (result.count === 0) throw new StaleStateError('Concurrent update detected');
  ```
- Result: If payment webhook, user cancellation, and expiry job hit the same booking concurrently, exactly one succeeds; the remaining two fail safely with zero side effects.

AGGREGATE RECOUNTING (Preventing Counter Drift):
- Instead of using arithmetic updates (`available = available - N`), Inventory Service recounts active seats from seat rows using `COUNT(*) FILTER (WHERE status = 'AVAILABLE')` inside every seat transaction. This ensures aggregate availability counts never drift or go negative.

7. HARD PROBLEMS #2: SAGA ORCHESTRATION, STATE MACHINES & COMPENSATION
================================================================================
Problem Statement:
A booking spans 3 microservices (Booking, Inventory, Payment). Local ACID transactions cannot span services. If Payment fails after seats are locked, locked seats will leak permanently.

SOLUTION: Orchestrated Saga Pattern with Persistent Audit Log & Compensation

BOOKING STATE MACHINE (8 States):
PENDING -> SEATS_HELD -> PAYMENT_PENDING -> CONFIRMING -> CONFIRMED
  │             │               │                 │
  └─────────────┴───────────────┴─────────────────┴───► FAILED / CANCELLED / EXPIRED

SAGA STEPS EXECUTION FLOW:
Step 1: HOLD_SEATS (Inventory Service)
  - Synchronous HTTP call from Booking Svc to `POST /internal/inventory/lock-seats`.
  - Creates `SeatSegmentLock` rows, marks seats LOCKED, updates SagaLog (HOLD_SEATS -> COMPLETED).
Step 2: CREATE_PAYMENT (Payment Service)
  - Synchronous HTTP call to `POST /internal/payments/orders`.
  - Creates Razorpay Gateway order, saves `PaymentOrder` (status CREATED), updates SagaLog (CREATE_PAYMENT -> COMPLETED).
Step 3: CONFIRM_SEATS (Inventory Service)
  - Triggered after Payment capture (via Webhook or Verify API).
  - Updates `SeatSegmentLock` status from LOCKED to BOOKED. Booking status becomes CONFIRMED.

COMPENSATION ENGINE (Reverse Step Execution):
If any step fails, `compensateAll()` executes inverse actions in reverse order based on `SagaLog`:
- If CREATE_PAYMENT fails -> compensateHoldSeats() calls `POST /internal/inventory/release-seats`.
- If CONFIRM_SEATS fails after payment capture -> initiateRefund() calls Razorpay refund API + releaseSeats().

EXPIRED BOOKING CLEANUP (Leader-Elected Cron Job):
- Process: Background job runs every 30s searching for `status IN ('PENDING', 'SEATS_HELD', 'PAYMENT_PENDING') AND lockExpiresAt < NOW()`.
- Multi-replica Coordination: Redis SETEX key `booking:expiry-job:leader` (25s TTL) acts as a distributed lock so only ONE instance runs cleanup per cycle.

8. HARD PROBLEMS #3: AUTHENTICATION, SECURITY & WEBHOOK INTEGRITY
================================================================================
1. Refresh Token Rotation (RTR) & Anti-Theft Protection:
   - Access Tokens: Short-lived JWTs (15 min) stored exclusively in-memory (Zustand).
   - Refresh Tokens: Long-lived JWTs (7 days) stored in HttpOnly, SameSite=Strict cookies.
   - Redis Storage: `refresh:{userId}:{deviceId}` stores the current `jti` (JWT ID).
   - Theft Detection Mechanism: If an attacker attempts to use an old/used refresh token, the stored `jti` mismatch triggers immediate deletion of the Redis key, revoking ALL sessions for that user/device.

2. Razorpay Webhook Raw-Body Signature Bug & Fix:
   - Problem: Express standard `express.json()` middleware parses incoming JSON bytes into Javascript objects. Re-stringifying this object alters key ordering and whitespace, breaking HMAC-SHA256 signature verification.
   - Solution: API Gateway injects `express.raw({ type: 'application/json' })` specifically for `/api/payments/webhooks/razorpay`. The untouched raw Buffer is passed directly to `payment-service` to verify `crypto.createHmac('sha256', secret).update(rawBuffer).digest('hex')`.

3. Internal Service Security (`X-Internal-Secret`):
   - API Gateway appends header `X-Internal-Secret: <SECRET>` to all downstream requests.
   - Downstream services reject any request to `/internal/*` routes lacking this secret, neutralizing direct port-exposure attacks in cluster environments.

9. CACHING, SEARCH (ELASTICSEARCH) & EVENT MESSAGING (KAFKA)
================================================================================
SEARCH SERVICE & ELASTICSEARCH ARCHITECTURE:
- Problem: Searching trains by station name requires matching partial strings, station codes, and handling typos (e.g., "Dehli" -> "Delhi").
- Solution: Elasticsearch 8.12 indices (`trains_index` & `stations_index`).
- Search Algorithm (`resolveStation`):
  1. Exact match on station code (`DEL`).
  2. Completion Suggester with `fuzziness: 'AUTO'`.
  3. Multi-match query across `name` and `city` fields.
- Event Synchronization: `search-service` listens to Kafka topic `inventory.seat-availability-updated` to update Elasticsearch `seatSummary` asynchronously.

KAFKA TOPOLOGY & CONSUMER IDEMPOTENCY:
- Kafka Topics:
  - `notification.otp-email`, `notification.welcome-email`, `notification.booking-email`
  - `payment.success`, `payment.failed`
  - `admin.schedule-created`, `admin.schedule-cancelled`
  - `inventory.seat-availability-updated`
  - `dlq.*` (Dead Letter Queue topics)
- Consumer Idempotency Pattern: Every Kafka consumer checks `IdempotencyRecord` table using `eventKey = {topic}:{eventType}:{entityId}` before executing business logic. If present, the message is acknowledged and skipped.

11. SCALABILITY & EXHAUSTIVE "WHAT IF" INTERVIEW SCENARIOS
================================================================================
Q1: What if traffic spikes by 100x during Tatkal opening (10:00 AM)?
  - Gateway Layer: Apply IP-based and User-based rate limiting (Redis Token Bucket).
  - Search Layer: Elasticsearch cluster scales read replicas; Gateway caches static route queries in Redis (TTL 30s).
  - Booking Layer: All services are stateless -> scale horizontally via Kubernetes HPA. PgBouncer pooler manages DB connection limits.
  - Locking Layer: Redis Lua scripts handle 100,000+ ops/sec effortlessly. Fail-fast locking rejects excess requests in < 5ms without touching Postgres.

Q2: What if two users click "Book" for the exact same seat at the exact same millisecond?
  - Requests enter Redis Lua script lock check. Exactly ONE request acquires key `booking:lock:seat:...`.
  - The losing request fails immediately with HTTP 409 Conflict ("Seats locked by another user").
  - Even if Redis fails, Postgres `FOR UPDATE NOWAIT` ensures only one transaction acquires row-level locks on `seat_inventories`.

Q3: What if the database primary node crashes mid-transaction?
  - AWS RDS Multi-AZ automatically initiates failover to standby replica (~30-60s).
  - In-flight transactions throw connection errors -> Saga catches and fails cleanly.
  - Kubernetes liveness probes reconnect pods to the newly promoted primary node once DNS resolves.

Q4: What if a network partition isolates Payment Service after Razorpay charges the user?
  - Razorpay fires webhook to Payment Service asynchronously.
  - When connection restores, Payment Service receives webhook, saves `CAPTURED` state, and publishes `payment.success` to Kafka.
  - Booking Service consumes Kafka event, updates state to `CONFIRMED`, and confirms seats. The system self-heals via eventual consistency.

12. KEY DESIGN TRADEOFFS & ALTERNATIVES CONSIDERED
================================================================================
1. Orchestrated Saga vs. Choreographed Saga
   - Chosen: Orchestrated Saga (Booking Service acts as central orchestrator).
   - Tradeoff: Introduces slight coupling between Booking Service and downstream internal endpoints.
   - Reason: Orchestration makes complex state transitions, audit logging (`SagaLog`), and failure recovery dramatically easier to trace, test, and debug.

2. Redis Distributed Locking vs. Database Pessimistic Locking
   - Chosen: Dual approach (Redis Lua first, Postgres FOR UPDATE NOWAIT as backstop).
   - Tradeoff: Increases operational complexity of maintaining Redis and Postgres in sync.
   - Reason: Redis provides sub-millisecond fail-fast performance to shield PostgreSQL from thundering-herd connection pool exhaustion.

3. Eventual Consistency for Search vs. Synchronous Indexing
   - Chosen: Eventual consistency via Kafka events to Elasticsearch.
   - Tradeoff: Search results may show seat counts that are stale by 1-2 seconds.
   - Reason: Decouples search availability from booking database writes. Real-time availability check is strictly enforced when clicking "Book".

FUTURE ROADMAP & ADVANCED ARCHITECTURAL UPGRADES:

Phase 1: High-Performance RPC & Inter-Service Messaging
- gRPC with Protocol Buffers (Replacing Internal REST):
  * Problem Solved: Internal REST HTTP/1.1 calls (`/internal/lock-seats`, `/internal/orders`) between microservices introduce high JSON serialization overhead, large text payloads, and connection setup latency.
  * Solution: Migrate all synchronous service-to-service Saga steps to gRPC over HTTP/2 using binary Protocol Buffers (`.proto`).
  * Benefits: 5x-10x faster serialization/deserialization, strongly-typed interface contracts across services, multiplexed persistent HTTP/2 TCP connections, and streaming RPCs for real-time status updates.
- Transactional Outbox Pattern with Debezium (CDC):
  * Problem Solved: The "Dual-Write Problem" — updating PostgreSQL and publishing a Kafka event in application code can fail halfway (e.g. DB commits, but app crashes before publishing to Kafka), leaving Elasticsearch or Notification service out of sync.
  * Solution: Write Kafka events into an `outbox` table in the SAME local Postgres ACID transaction as the business entity. A Debezium CDC worker reads the Postgres Write-Ahead Log (WAL) and streams events to Kafka with 100% durability and zero dual-write bugs.

Phase 2: Advanced Fault Tolerance & Concurrency Controls
- Circuit Breakers & Bulkhead Isolation (Opossum / Resilience):
  * Problem Solved: If `inventory-service` experiences degradation, `booking-service` HTTP request threads pile up waiting for responses, causing cascading thread pool exhaustion across the entire API Gateway.
  * Solution: Wrap internal gRPC/REST calls in Circuit Breakers (with configurable error thresholds, fallback responses, and automatic half-open trial states) and Bulkhead isolation (capping parallel concurrent calls per downstream service).
- Single-Threaded Seat Actor Model (Redis Streams / BullMQ):
  * Problem Solved: When hundreds of concurrent users attempt to book overlapping segments on the exact same seat, Postgres `FOR UPDATE NOWAIT` causes high transaction rejection and retry storms.
  * Solution: Serialize seat mutation requests using a single-threaded Actor pattern backed by Redis Streams (one queue per train schedule). Mutations for a specific seat execute sequentially in-memory, eliminating database lock contention entirely.

Phase 3: Resilient Observability & Rate Control
- OpenTelemetry Distributed Tracing & Jaeger Integration:
  * Propagate W3C `traceparent` headers across Gateway -> gRPC services -> Kafka headers -> Async Consumers. Visualize full end-to-end request spans in Jaeger to pinpoint microsecond latency bottlenecks.
- Redis Token Bucket Distributed Rate Limiting:
  * Deploy sliding-window rate limiters at the API Gateway level (keyed per User ID and Client IP) to shield the system from bot scripts during peak Tatkal hours.

Phase 4: Global Availability & Distributed SQL
- Multi-Region Active-Active Replication (CockroachDB / YugabyteDB):
  * Migrate service datastores to distributed SQL databases spanning multiple geographic regions (Mumbai, Delhi, Hyderabad). Utilize Raft consensus to guarantee strict CP serializable isolation for inventory locks while maintaining multi-region high availability.
