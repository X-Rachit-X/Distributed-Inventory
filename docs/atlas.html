Tessera · distributed reservation engine

How Tessera fits together

Eight diagrams, each showing one mechanism. The single idea underneath all of them: PostgreSQL refuses to store two live bookings of the same seat with overlapping journeys. Everything else makes the system faster, fairer or more resilient, and none of it is needed to prevent an oversell.

01 · SYSTEM MAP

Eight services, one authority

Every request enters through the gateway. Only the inventory engine may write allocations. Services own separate databases and announce changes through Kafka using an outbox; reconciliation is the one component that reads every database.

Where: services/gateway/src/index.js (routes) · deploy/compose/docker-compose.yml (infrastructure) · deploy/compose/init/postgres/01-databases.sql (one DB per service)

02 · THE CORRECTNESS FLOOR

Only the bottom layer can stop an oversell

Each layer has a different job. If an upper layer breaks, the system gets slower, less fair, or needs a repair, but no seat is sold twice, because the database itself refuses the row.

Where: services/inventory-engine/sql/migrations/010_inventory_core.sql (constraint) · engine/reserve.js (catches 23P01 → 409)

03 · 1,000 BUYERS, 1 SEAT

Why a row lock sits in front of the constraint

Both designs below are correct: neither ever sold the seat twice. The difference is how waiting is organised. A GiST exclusion constraint inserts first and then waits on any conflicting transaction still in flight, so concurrent inserters wait on each other in cycles. Locking the seat's row first turns that tangle into a single queue.

Where: engine/reserve.js steps 3–4 (sort, lock) · lab/src/strategies/index.js (F vs F2) · docs/benchmarks/RESULTS.md

04 · ONE BOOKING

The request returns early; a saga finishes the job

The API stores the intent in one fast transaction and replies 202. A saga worker then drives hold → charge → confirm, one step per claim, with an idempotency key derived from the saga id on every call. A crash between steps loses nothing, because progress lives in a row.

Where: services/reservation/src/index.js (1–5) · saga/orchestrator.js (6–10) · shared/src/outbox + notification/src/index.js (11)

05 · SAGA STATES

Every failure has a defined way out

The forward path runs down the left. Each failure branches right into a compensation that undoes what already happened. A database trigger rejects any arrow not drawn here, and every money-ambiguous case ends with a human, not a guess.

Where: services/reservation/sql/migrations/010_reservation_core.sql (trigger) · saga/orchestrator.js (STEP_POLICY, #step)

06 · OUTBOX TO CONSUMER

Never lost, never applied twice

The event is a row written in the same transaction as the business change, so it exists only if the change committed. The relay publishes first and marks second (at-least-once). The consumer writes its dedupe marker in the same transaction as its effect, so a repeat delivery changes nothing.

Where: packages/shared/src/outbox/writer.js · outbox/relay.js (#claim) · consumer/index.js (createIdempotentHandler)

07 · UNKNOWN PAYMENTS

A timeout is a question, not an answer

If the provider doesn't answer, the money may already have moved. Marking it failed strands a paying customer; retrying may charge twice. So the payment becomes UNKNOWN and the service asks the provider what happened, using its own idempotency key as the reference.

Where: services/payment/src/service/payment.service.js (charge, resolveUnknown, handleWebhook) · providers/fake.provider.js (fault modes)

08 · READS VS WRITES

Search may be stale; booking never is

The booking path talks only to the authority. Search answers from a projection that inventory events mark as dirty and a refresher rebuilds by re-reading inventory. A stale search result can cost a user one retry; it can't sell a seat twice.

Where: services/discovery/src/index.js (cache, consumer) · projection.js (refresher) · search-index.js (ES, breaker, fallback)
